# 规划（L0–L4）

适用于：用户要的不是结果，是一份能照着走的东西。

**核心差异**：计划的价值在取舍和先后，不在事项的罗列。只给一条路 = 没做规划，只是复述。

---

## L0 定边界

四件事，缺一件计划就会飘：

| 要素 | 问法 | 缺失后果 |
|---|---|---|
| 目标 | 做成什么样算成？ | 计划没有终点 |
| 约束 | 什么时候要？几个人？多少钱？ | 计划做不出来 |
| 范围外 | 什么明确不做？ | 计划无限膨胀 |
| 决策人 | 谁拍板？ | 计划没人认 |

四个问题一次问完太密。按这个顺序，一次一个：**时间 → 人手 → 不能动的 → 谁拍板**。

写进 `plan.md` 开头，四行。

---

## L1 列候选路

**至少两条**，而且必须真的不同，不能是同一方案的微调。

常见的真分叉：

- 快而糙 vs 慢而稳
- 自建 vs 采购
- 先做窄的一个场景跑通 vs 一次铺开
- 先做能看的（demo）vs 先做能用的（骨架）

写法：

```
路线甲：<一句话说清打法>
  代价：<时间 / 钱 / 人力>
  风险：<最可能翻车的地方>
  适合：<什么条件下选它>

路线乙：…
```

两条路都要能给出一句"选它的理由"。给不出，说明这条是凑数的。

---

## L2 选路拆解

选定后拆里程碑：

- **3–7 个**。少于 3 说明粒度太粗，多于 7 说明该分子项目。
- 每个里程碑要有：**产出物 + 验收判据 + 依赖**
- 标出**关键路径**：延迟会拖垮整体的那一条
- 标出**回滚点**：哪一步做错了能退回来，退回成本多大

判据必须能被第三方验证。"完成用户模块"不行，"用户能注册、登录、改密码，三个流程跑通"才行。

---

## L3 出计划

表格，一屏能看完：

| 阶段 | 产出 | 判据 | 依赖 | 风险 |
|---|---|---|---|---|
| M1 | | | | |
| M2 | | | | |

要求：

- 每行都能被问一句"怎么知道这步成了"，答不出就重写
- 不出现"加强""提升""优化""推进"这类词，它们无法验收
- 风险列写具体的（"第三方接口审核要 2 周"），不写抽象的（"存在不确定性"）

---

## L4 落地

1. 用户认可 → 存 `plan.md`，问一句："要不要现在开始第一步？"
2. 开始 → **转 B 路线**，计划直接作为 G1 的步骤，不再重问目标
3. 用户不认可 → 回 L1 换一条路，不要在原路上打补丁

---

## 常见失败

| 症状 | 原因 | 处理 |
|---|---|---|
| 用户说"这不像计划，像任务清单" | 只有事项，没有先后和依赖 | 补关键路径和依赖列 |
| 计划很漂亮但没人执行 | 忽略了约束（人手、时间） | 回 L0 补约束，砍到能做的量 |
| 每个里程碑都"待定" | 拆解不够，只是把目标重述了一遍 | 每个里程碑必须有一个具体产出物 |
| 用户看完说"我知道啊" | 全是常识，没有取舍 | 回 L1，把两条路的代价差异写狠一点 |
| 计划一改再改 | 目标本身没定 | 回 L0，先定死目标再谈路径 |

---

## 计划的颗粒度参考

- 一周内的事：按天拆
- 一个月：按周拆
- 一个季度：按里程碑拆，不排到天
- 超过一个季度：只给阶段和判据，日期留白

颗粒度错了，计划一定会被现实打乱，然后没人再信它。
