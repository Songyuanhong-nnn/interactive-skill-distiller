# 调研套路

调研不是为了显得专业，是为了回答三个问题：

1. 这东西**别人已经做过**吗？（避免重复造，或者干脆复用）
2. 这个领域**正确的说法**是什么？（术语直接决定触发词质量）
3. 这类东西**通常怎么失败**？（易错点从哪来）

每条调研结论必须能回答："它改变了我的哪个决定？"答不出来的记录，不要写进台账。

---

## 四类来源，按顺序查

### 1. 本地已有 skill（先查这个，最快）

```bash
ls ~/.workbuddy/skills/          # 用户级
ls ./.workbuddy/skills/          # 项目级
ls ./.claude/skills/ 2>/dev/null
```

判定：
- 功能高度重叠 → 不新建，走 REFINE 扩展已有 skill
- 部分重叠 → 新建，但在"何时不用"里写明分工
- 无重叠 → 继续

读对方 SKILL.md 时只看两处：description（边界在哪）和流程步骤（粒度多细）。

### 2. 规范与平台约定

要确认的：
- frontmatter 必填字段（name / description）与可选字段
- name 正则：`^[a-z0-9]+(-[a-z0-9]+)*$`，1–64 字符，需与目录名一致
- description 长度上限（通常 1024 字符），必须同时含 WHAT 和 WHEN
- 目标平台的 skill 存放路径

规范来源：https://agentskills.io/specification

### 3. 领域参考（外部）

用 WebSearch，按这个顺序搜：

| 搜什么 | 目的 | 例子 |
|---|---|---|
| `<领域> best practice` / `<领域> 流程` | 拿到标准做法和术语 | "竞品分析 框架" |
| `<领域> workflow steps` | 对照别人拆的步骤粒度 | "competitor monitoring workflow" |
| `<领域> common mistakes` / `<领域> 失败案例` | 易错点素材 | "竞品分析 常见错误" |
| `site:github.com <关键词> skill` | 找现成实现参考 | 找同类 skill 结构 |

**术语是最高价值产出。** 用户说"过一遍文案"，领域里叫"一致性校验（consistency check）"——后者才是能命中触发、能让 AI 理解精确意图的词。

### 4. 反例与边界

专门找"这套方法什么时候不管用"。来源：
- 用户自己的失败经历（访谈维度 6/7）
- 社区吐槽、issue、复盘文章
- 方法论的适用前提（规模、行业、团队大小）

反例写进"何时不用"，能把误触发率降一大截。

## research.md 记录格式

每条一行块，追加写，不改旧条：

```markdown
## R-003 · 2026-11-09 · 领域术语
- 来源：<URL 或 本地路径>
- 查到了什么：竞品监控在行业里标准叫法是 "competitive intelligence monitoring"，
  拆成 采集 / 归因 / 预警 三段
- 改变了什么：把原本笼统的"看竞品"拆成三个步骤；触发词补上英文术语
- 可信度：高（行业标准文档 + 2 个独立来源一致）
```

字段说明：
- **来源**：必须可回溯。本地文件给路径，网页给 URL
- **查到了什么**：事实，不带评价
- **改变了什么**：这是重点。写不出影响 = 这条没用，删掉
- **可信度**：高（多方一致）/ 中（单一来源）/ 低（推测，需验证）

## Gate 判据

进访谈前必须满足：

- [ ] `research.md` ≥ 3 条有效记录（每条都有"改变了什么"）
- [ ] 至少 1 条改变了 skill 的**边界判断**（新建 vs 复用、做什么 vs 不做什么）
- [ ] 拿到 ≥ 3 个领域专有术语，可直接做触发词
- [ ] 拿到 ≥ 1 条典型失败模式，可直接做易错点

达不到就继续查，或者老实告诉用户"这块资料太少，先按你的经验来，后面有样例再补"。

---

## 什么时候停止调研

调研会无限膨胀，设个止损：

- 连续两条记录都没改变任何决定 → 停
- 搜到的东西开始重复 → 停
- 用户已经在催了 → 停，用现有信息出骨架，标注"待验证"

调研服务于访谈，不是反过来。
