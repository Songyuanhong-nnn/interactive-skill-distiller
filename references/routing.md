# 意图路由

路由不是关键词匹配，是判断三个结构特征。30 秒内做完，只做一次。

---

## 三个结构特征

| 特征 | 问题 | 判读 |
|---|---|---|
| 生命周期 | 这个产出物是一次用，还是以后反复用？ | 反复用 → A；一次用 → B/C |
| 目标形态 | 用户要的是结果，还是方法？ | 结果 → B；方法 → A/C |
| 终点 | 这件事有没有一个"做完了"的时刻？ | 有 → B；要排先后 → C |

三条都指向同一路线时，直接定，不必问。

---

## 信号表

### 强信号（出现即可定）

**A 蒸馏**
- "每次都""下周还得再来一遍""每周都要"
- "固化""标准化""沉淀""做成工具""自动化"
- "下次直接就能用""不用再交代一遍"
- 用户已经在描述一套流程，而不是一件事

**B 引导执行**
- 具体交付物名词：文案、方案、报告、代码、章节、PPT、邮件
- "帮我写""帮我改""帮我整理""做一份"
- 用户手上有材料，但不知道从哪下手

**C 规划**
- "先做什么后做什么""哪个优先""排期""路线图""里程碑"
- "半年""这个季度""分几步走"
- 用户在问"怎么安排"，不是"怎么做"

### 弱信号（要结合上下文）

| 说法 | 可能是 | 怎么判 |
|---|---|---|
| "怎么做" | B（要方法）或 C（要计划） | 有没有交付物名词？有 → B；只有顺序 → C |
| "帮我搞定" | B 或 A | 交付一次就完 → B；以后还要 → A |
| "整理一下" | B 或 A | 整理文件 → B；整理流程 → A |
| "优化一下" | 全是 | 问优化什么，别猜 |

### 容易误判的四种

1. **"帮我写个脚本，以后每天跑"** → 看着像 B（写脚本），其实是 A。判据是"以后每天"——交付物是复用工具。
2. **"帮我写个 skill 介绍页"** → 出现 "skill" 但这是 B。判据是产出物是一张页面，不是技能本体。
3. **"帮我规划一下这个 skill 怎么做"** → 混合。先 C 出计划，计划里含 A 的步骤。
4. **"我想做点东西，但不知道做什么"** → 三条都不成立。这不是路由问题，是目标没定。先做 G0（定终点），定完再判。

## 拿不准：只问一次

一句话二选一，带推荐，不要连环追问：

> 这件事你是一次做完就完，还是以后要反复用？
> A 一次用完就算（我按执行来带）
> B 以后还要反复用（我按蒸馏来做，产出可直接调用的技能）

选 A → B 路线；选 B → A 路线。
如果用户说"既要又要"→ 先 B 做出第一版，D4 时提议转 A。

---

## 混合意图的处理顺序

| 组合 | 顺序 | 理由 |
|---|---|---|
| 规划 + 执行 | C → B | 先定路线再动手，避免边做边改方向 |
| 蒸馏 + 执行 | A 的 P0–P2 → 卡住则 A→B 试做 | 说不清就先做一小段，从修改里反推 |
| 三个都要 | C 优先 | 计划里天然包含 A 和 B 的位置 |

---

## 判错了怎么修

用户说"我不是要这个"时：

1. **不辩解，不解释为什么判错**。一句话确认新意图："明白，这是要直接做出来，不是做工具。"
2. 改 `state.yaml` 的 `intent`，`intent_history` 追加一条（旧意图 / 新意图 / 触发原因）
3. **已产出的档案不删**。B 的 `goal.md` 可以改写成 A 的 `problem.md`，反之亦然
4. 从新路线最早未完成的阶段继续，**不重头问已知信息**

---

## 路由不该做的三件事

- ❌ 为了判得准而连环追问 → ✅ 最多问 1 次，判错就换道
- ❌ 因为出现某个词就定路线（"skill""计划"都是高频词）→ ✅ 看产出物的生命周期
- ❌ 在路线内部反复重判 → ✅ 判一次，只有出现换道信号才改
